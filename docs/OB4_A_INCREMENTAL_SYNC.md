# OB4-A 有界增量与恢复验收

## 范围与复用

仍由 collect_game 请求 GameBanana Generic_NewAndUpdated，normalize_record 标准化、import_samples 比较及事务入库。采集器仅增加可选 start_page，默认行为不变。继续使用现有 OS 文件锁、来源请求保护、Backup API 和事件规则。不修改 schema、用户偏好或任何旧回填检查点。

默认每游戏最多3页，可选1至10页；全部游戏最多6款，逐游戏逐页串行。当前单游戏每页20条，全部游戏每页10条。默认全部游戏正常请求上限18次，临时失败每页至多重试一次，上限36次。显式提高页数到10时正常请求至多60次、含重试至多120次；429处理Retry-After后停止，不执行后续页或游戏。首个普通失败停止该游戏后续页，但继续其他游戏。已验证页保留为待确认候选。

不因命中已有作品或某个旧时间停止。达到页数上限仍 coverage=incomplete。只有API分页元数据确认末页，才显示“完整检查（仅本次来源末页）”，不把它当成时间窗口完整性或永久无遗漏的保证。

## 正式检查点与预览日志

- 正式检查点放在现有 sync_runs.error_summary.web_sync 内，与作品、事件和同步日志同事务提交，不需要额外表或跨文件事务。记录每游戏连续页边界、每页数量、检查页、成功检查时间、最近成功页时间、最新来源发布/更新时间及ID、失败原因和待续扫标志。
- 只检查、取消、超时、备份失败、SQL回滚都不会推进正式检查点；用户确认后才提交。无作品变化仍可写同步日志和检查点，但不生成无意义数据库备份。
- logs/web_sync/task.json 保存未提交进度和预览候选；原子替换，切换任务时保留上一份日志。API重启可恢复有效预览；十分钟过期或数据库/同步日志基线变化时拒绝确认，要求重新检查。原文件损坏时保留并报错，不静默覆盖。
- API在请求中断时，启动后显示等待续扫，未提交页重新检查。若数据库已提交而日志更新失败，重启后从sync_runs识别已提交状态，不误报未提交。
- 旧图片/分级回填检查点含义不同，不直接用于网页作品同步，避免覆盖其进度。

## 续扫规则与限制

普通检查始终从首页开始。点击“继续扫描”时读取**已提交**的每游戏边界，再查首页及边界重叠页。例如已提交1–3页，默认三页请求为1、3、4；下一轮提交后为1、4、5。预算1或2主要用于首页/重叠复核，未必能推进边界。每页数量改变时从首页重新检查，不能复用旧页码。

未确认预览不充当已提交游标：继续会重查相同范围，不跳过未入库数据。重叠可以降低分页移动造成的漏采风险，但不能证明绝对无遗漏；因此coverage保持incomplete。不要用本功能声称完成30天全量回溯。

## 统计定义

互斥分类：新增、可靠来源更新、仅资料变化/更新证据不足、无变化、跳过。缺少updated_at另外作为诊断数，不能与互斥分类相加。

`原始返回记录 = 已分类 + 重复记录 + 未能分类记录`

`已分类 = 新增 + 来源更新 + 仅资料变化/证据不足 + 无变化 + 跳过`

重复包含页内及跨页重复；请求失败次数与已知的返回记录数分开统计，无法知道失败页包含多少作品时不编造数量。失败或身份异常页中的已知返回记录列入未能分类，不进入导入候选。去重作品数另外显示。

原OB3-B例子：60 = 新增43 + 来源更新2 + 仅资料变化1 + 无变化14。差额不是丢失了一条作品，而是旧界面漏显资料变化类别。

## Windows验收

1. 用现有关闭、启动入口重启工具盒；不要关闭其他手动服务。
2. 最新MOD选择游戏，页数保持3，检查各页/请求数、互斥分类合计、coverage和失败原因。

# OB2-B 图片诊断与验收

## 当前实现与本轮变化

- 列表 API 从 `thumbnail_url` 生成 `preview_urls`；旧字符串记录或缺失缩略图时会退回已有 URL，不猜测文件名。因此旧数据不保证具备独立小图，本轮不改数据库。
- 列表前三张已有 eager/high，其余图片在接近视口时挂载并 lazy/low 加载；固定 16:10 占位防止布局跳动。
- 详情仅渲染当前 `image_url` 高清原图，缩略图条使用 `switch_url`，缺失时使用 `thumbnail_url`。不预加载所有原图。
- 详情期间原列表保留 DOM；没有添加随机参数、代理或禁用缓存。浏览器是否实际命中第三方缓存仍需真实网络检查。
- 本轮增加卡片、高清图及缩略图失败后的手动重试；失败状态停止加载提示，重试使用原 URL。保持原图清晰度、导航及已阅逻辑。

## 验证边界

前端测试和隔离 Chrome 测试使用模拟 API 与 SVG，只验证懒加载、重试和导航行为，不测量 GameBanana/CDN 性能。
真实冷/热缓存的图片请求次数、传输量、首屏完成时间、重复传输、缓存命中和失败数均尚未验证；不能宣称下载速度改善，不能据此归因 CDN。

## 本机真实网络验收

1. 使用同一浏览器、窗口尺寸、游戏、筛选、页码和网络条件，选含六张图的 MOD 732438。打开开发者工具 Network，勾选 Preserve log，**不要勾选 Disable cache**，按 Img 过滤。
2. 冷缓存轮：在独立测试浏览器配置中清除缓存，然后进入最新 MOD；记录首屏可见图片最后一个 load 的时间（可通过 Performance 时间线确认），记录请求数、Transferred、失败数。
3. 滚动第二屏；确认非首屏按需出现请求。打开详情，只应请求当前原图和小缩略图；依次切换六张，再返回列表，再打开详情。每阶段记录新增图片请求、传输量、重复 URL、memory/disk cache 或 304 状态。
4. 热缓存轮：不清缓存、不改变条件，再执行同样步骤。请求条目数不等于重复下载量；缓存条目应独立统计。304 仍有网络往返，不能当作完全无请求。
5. 使用修改前版本与本版本分别完成以上两轮才可比较性能；本轮没有改动已有加载调度，不预期凭空减少其请求预算。
6. 断网或通过 DevTools 阻止单个图片 URL，确认失败提示和重试；解除阻止后重试成功。无图提示与失败提示应不同。

可将 HAR 保存在本机忽略的 logs 目录；其中可能含浏览信息，不上传。若图像请求耗时较高，再依据 Timing 区分排队、连接、TTFB 与传输，不先认定 CDN 原因。
